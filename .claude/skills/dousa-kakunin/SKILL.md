# 動作確認書（テックプット版）

PR を出す前に、レビューする人が「手順どおりに操作すれば同じ画面になる」と確かめられる確認書を作る。撮影は `/auto-test`（Playwright）、表の体裁はこのスキル。

## まず守ること（テストする人の気持ちで作る）

- **証跡にならない画像を貼らない。** 0 件の一覧・読み込み中・エラー画面・ボタンが出ていない画面は証跡にならない。0 件しか撮れないなら手順かデータが違う。seed やデータを足して、結果が出る状態で撮り直す
- **手順の対象と画像の対象を同じにする。** 手順に書いたアカウント・テナント・記事・コースと、画像に写っているものを一致させる。食い違うと「手順どおりにやったら別の人が出た」になる
- **前提の状態を今のデータで満たす。** 「未公開の記事」の項目を公開済みの記事で撮らない。前の項目の操作で状態が変わったら、戻すか手順を変える
- **件数・日時は撮った時点の値にする。** 撮り直したら「12 件」「2026/11/17」も書き換える
- **前の項目で作った状態が要る項目は、前提の作り方を最初から書く。** 「No.3 の手順で」に頼らず、【前提の状態を作る】ログイン（誰で）→ 開く → 入力 → 保存 を番号付きで書いてから【確認の操作】に進む
- **説明も画像も無い項目を残さない。** 撮れない項目は J 列「未実施」、K 列に理由を書く
- **撮れたことと、見るべきものが写っていることは別。** 貼る前に 1 枚ずつ目で見る

## シートの形

| 行 | 内容 |
|---|---|
| 1 | タイトル `【テックプット】<機能名> 動作確認書`（紺 #1c4266・白・太字・14pt） |
| 2 | ■ 対象 PR（バックエンド #番号 / フロント #番号）と、確認したブランチ |
| 3 | ヘッダー（紺 #1c4266・白・太字）: `No. / 確認項目 / 前提条件 / 操作手順 / 入力値 / 期待結果 / 種別 / 設計技法 / 証跡 / 結果 / 備考` |
| 4〜 | 項目ブロックの繰り返し |

- ヘッダーまでを固定（ウィンドウ枠の固定 3 行）。全体は折り返しあり・上揃え
- 列幅の目安: A44 / B331 / C263 / D463 / E183 / F581 / G100 / H100 / I200 / J100 / K400 px
- 結果（J 列）は OK / NG / 未実施 のどれか。備考（K 列）は NG・未実施の理由だけ

### 項目ブロック

```
行N    項目行（A:K を薄紺 #dbe5f1・太字）。No. は仕様書・設計書の項番と揃える（欠番可）
行N+1  「動作1: <操作>」（B 列・水色 #cfe2f3・太字）
行N+2〜 その操作のスクショ（幅 900px）
…      動作2, 動作3 … と続ける
最後   「〜になっていれば OK」の確認行（水色 #cfe2f3・太字）
```

- 動作の番号は項目ごとに 1 から振り直す
- 動作の文は、矢印が指している UI の名前を「」で書く。良い例「動作2: サイドバーの「コース一覧」をクリック」。悪い例「動作2: 一覧」
- 修正前と修正後を比べる項目は **同じ行に左右で並べる**（左 = 修正前を B 列、右 = 修正後を G 列）。上下に分けない

## トップ画面からの到達手順

- 項目の画面まで、**ログイン画面からどこを押すか** を書く。「コース一覧を開く」で済ませず、押す場所に矢印を入れたスクショを付ける
- ログインの入口は `.claude/rules/project/techput-overview.md` の表どおり（受講生 `/tenant/:tenantId/users/login`、管理者 `/admin/login`、マネージャー `/manager/login`）。アカウントは seed（`test_user0@gmail.com` など）と、そのテナント番号を書く
- 「アドレスバーに URL を入力」は手順に入れない。押して進めない画面（直リンクの 404 確認など）だけ例外として、パスを書く
- 同じ画面の項目が続くときは、到達手順は最初の項目にだけ書き、他は「No.X の手順でコース一覧を開く」の 1 行にする。ただし前の項目で作った状態が要る項目は、上の「最初から書く」に従う
- `localhost:5173` などローカルの URL はシートに残さない。画面はパス（`/admin/courses`）で書く

## データが変わる項目は表を入れる

登録・更新・削除・並べ替え・公開切り替えのように DB が変わる項目は、確認行の直前に次を入れる。

1. 見出し「▼ ○○で変わるテーブル: `<テーブル名>`（日本語名）— 変わる列」
2. 操作の **前** と **後** の SELECT 結果を、セルの表で並べる（列名は SQL のまま。変わったセルを黄色、真下に「↑ 値 = 意味」）
3. 論理削除なら「行は消えず `deleted_at` に日時が入る」と書く

- 操作の前に SELECT を取って控える。控え忘れたら推測で埋めず、「今の値だけ」と書いた表 1 つにする
- SELECT は Adminer（`http://localhost:8080`、サーバ `db`）で取る。画面のスクショではなく、値をセルの表に起こす
- 多テナントの機能は `tenant_id` 列を必ず表に入れる。「他テナントで見えない」の項目は、別テナントのアカウントで開いた画面と、DB が変わっていないことの両方を載せる

### データタブ

表が大きい（20 行を超える）ときは、「データ」タブに置いて項目から飛べるようにする。

- タブ名は「データ」1 つ。項目ごとに見出し行（オレンジ）→ テーブル名 → SQL → 前と後の表 → 注記
- 項目の見出しを `=HYPERLINK("https://docs.google.com/spreadsheets/d/<ID>/edit?gid=<gid>#gid=<gid>&range=A<行>", "見出しの文字")` にする。`#gid=` だけの相対リンクは同じタブ内で移動してしまうので、フル URL にする
- データタブに書き込んだ後は行がずれるので、リンク先の行を取り直す

## 結果が分かれるテストはブロックを分ける

公開と非公開、成功と失敗（422）、本人と他人（404）のように結果が分かれるものは、1 テスト 1 ブロックにする。

- 時系列で混ぜない（「3 件作る → 公開・非公開・削除 → 結果 3 件」にしない）
- 見出し行を色分けする: 共通 #dbe5f1 ／ 成功 #d9ead3 ／ エラー #f4cccc ／ 対象外 #e7e6e6
- 全件で同じ画面（ログイン直後など）は、先頭の「■ 共通」ブロックに 1 回だけ載せる
- 一覧に全件が並ぶスクショは、ブロックごとに **そのテストの行だけを指した版** を載せる

## スクショと矢印

- 撮影は `/auto-test` で PC 1440×900 とスマホ 375 幅。保存先は `docs/test_evidence/<機能名>/`（コミットしない）
- 画像は中身の範囲だけ切り抜き、シートには「挿入 → 画像 → セルの上に画像を挿入」で幅 900px にして貼る。次のラベルと重ならないように、画像の高さ ÷ 21px ＋ 2 行を空ける
- 矢印は文字に被せない。押す場所を赤枠で囲み、矢印は枠の少し外で止める
- 矢印や注記の文言を変えたいだけなら、画像を撮り直さない。シートの「挿入 → 図形描画」で上から置く

## 書くときの言葉

- 開発者向けの言葉（コマンド、ファイルパス、`rails` `npm`、変数名）を手順に書かない。画面の言葉で書く
- 1 セル 250 字以内。スクショで分かることを同じ文で繰り返さない
- 状態名・ボタン名は画面の表記に合わせる（「公開」「下書き」など）

## 上書き・取り違えをしない

- 作業の最初に、対象のスプレッドシートとタブを 1 行で宣言し、途中で変えない。題名の似たコピーがあれば、どれが正本かを確かめてから書く
- 書く前に今の値を読み、期待した値と同じときだけ書く。違えば止めて報告する
- 人が手で直したもの（セル結合・列幅・色・図形描画・貼り直した画像・文言）を、後から上書き・解除しない。全体の書き直しや書式の一括適用は最初の 1 回だけ
- 直した後は読み直して、何が変わったかを報告に書く

## 仕上げの確認（「できた」と言う前に毎回）

1. 先頭 3 行とヘッダーの形、列幅が上の型どおりか
2. PDF に書き出して（ファイル → ダウンロード → PDF）、画像が動作ラベルの直下にあり、表や確認行と重なっていないか
3. 結合した行が 1 行の高さで切れていないか
4. 全項目で、手順・画像・表の対象（アカウント・テナント・レコード）が一致しているか
5. J 列・K 列が事実と合っているか（未実施は「未実施」と理由）
6. 確認した結果（直した点・残った点）を 1〜2 行で報告する

作った本人だけで済ませず、別の人（またはレビュー役のエージェント）に、対象の行と期待する状態を渡して見てもらう。
